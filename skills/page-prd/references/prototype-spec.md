# 业务需求原型生成规范 v4.1（2026-10-22）

版本变更记录见 `CHANGELOG.md`。

## 一、定位与触发场景

### 1.1 触发场景（四类）

四类场景（A 生成 / 迭代、B 人工修改回传、C 对话修改说明、D 导出说明 Markdown）的识别信号、判定顺序和追问话术以 `SKILL.md`「何时触发」为准，本规范不重复。各场景对应的规范章节：

| 场景 | 规范章节 |
|---|---|
| **A. 生成 / 迭代原型** | 第二章起，工作流程见第七章 |
| **B. 人工修改回传** | 七·补2 |
| **C. 对话修改说明** | 七·补4 |
| **D. 导出说明文本** | 七·补5 |

- **场景 B 严禁重新生成原型** —— 重生成会把用户在浏览器里改的说明整块冲掉
- **场景 C 严禁顺手改原型** —— 除非用户明确同意（见 `SKILL.md` 一致性判定表）
- **场景 D 严禁顺手改文件** —— 只生成 md 副本；且必须做冲突预检（用户在浏览器改过说明的话，先走 B 合并再导出）

### 1.2 产物形态

需求进来 → 产出单个 HTML 文件：
- **左侧（约 62%）**：B 端后台功能原型，内部为「系统菜单 + 内容主区」布局，视觉风格以 `assets/template.html` 为准
- **分割线**：竖向**虚线** + 竖排「分割线」字样（`writing-mode:vertical-rl`），上下贯通；**虚线与文字均用深黑色**（`#000`）
- **右侧（约 38%）**：需求说明（PRD 性质），两章结构 + 编号气泡与左侧双向联动

**页面宽度：全宽自适应，不留两侧空白**（设计基准 1440，最小宽度 1280）。

## 二、左侧功能原型区（必须严格遵守）

### 2.1 端与布局
| 项 | 规范 |
|---|---|
| 端 | 用户未提要求时，**默认 PC 端**；只保证 1440px 总宽度下完美显示，不做移动端适配 |
| 系统布局 | **左右结构**：左侧为系统菜单（导航栏），右侧为内容主展示区 |
| 顶栏 | 左：logo/系统名；中：全局搜索框；右：通知铃铛 + 用户头像/姓名 |

### 2.2 技术栈
1. 只输出**一个独立的 `index.html`**，不依赖任何本地文件和构建工具，双击即可在浏览器打开
2. 组件外观用 **HeroUI 官方编译样式 `heroui.min.css`（CDN 引入）**，页面布局用 **Tailwind v4 浏览器版（CDN 引入）**，交互用 **Vue 3（CDN 引入）**，不用 npm、不经构建。CDN 地址固定版本，与 `assets/template.html` 一致（见 8.1），不用 `vue@3` 这类会随新版本变化的地址
3. 所有数据用 JS 里的假数据（**mock 数组，8~10 条贴近真实格式的虚构中文业务数据**），不调任何接口
4. 视觉风格：B 端后台风格，按钮、输入框、下拉框、复选框、单选框、标签、卡片、表格、弹窗、抽屉、页签一律用 HeroUI 的组件类名和模板里封装好的 Vue 组件（见第六章），配色、圆角、阴影、字号用 HeroUI 主题变量；图标一律用 lucide 内联 SVG，禁止用 emoji 当图标

### 2.3 列表页交互
- 页面标题 + 一句说明文字 + 右上角主操作按钮（如「录入线索」）
- 筛选卡片：关键词/下拉筛选项 + 重置 + 查询（查询为主按钮）
- 表格：HeroUI 表格（`table-root`），状态用浅底彩色标签（`chip chip--soft`），行操作用「更多」按钮（`<hui-menu>`）展开下拉菜单
- 底部分页：「共 N 条」+ 页码

### 2.4 详情页 / 新增页 / 编辑页
- **布局结构化，字段分组展示**（每块一个 HeroUI 卡片，标题用 `card__title`）
- 详情页头部：头像/首字圆标 + 名称 + 状态标签 + 编号等次要信息 + 右上角编辑/主操作按钮
- **当字段较少时，新增页、编辑页做成弹窗即可**（不必单独页面）

### 2.5 弹窗类页面交互
- 居中弹窗 + 半透明遮罩，右上角 × 关闭
- 字段必填项标红色 `*`，下拉用「请选择 XX」占位
- 底部右侧：取消（次按钮）+ 保存（主按钮）

### 2.6 多页面
列表/详情/表单等全部在**同一个 index.html 内**切换（Vue 条件渲染），不拆多文件。

## 三、右侧需求说明栏（v3.0 结构）

### 3.0 组织粒度：一个系统 = 一份 index.html，说明随菜单联动（核心规则）

> **功能点的入口在哪，就把这个功能点的需求说明写在哪。**

⚠️ **曾犯过的错误（勿重犯）**：把「一个菜单 = 一个 index.html」当成这条规则的推论。用户明确纠正：**多个菜单属于同一个原型，必须在同一个 HTML 文件里**。

| 层级 | 单位 | 行为 |
|---|---|---|
| 系统 | 一个 `index.html` | 所有菜单都在这一份文件里；新菜单需求**在原文件上加菜单**，不新建文件 |
| 菜单（一级导航） | 右侧说明的切换单元 | 点左侧菜单 → 左侧内容区**和右侧说明同时切换**（每个菜单一个说明 pane） |
| 功能点（列表/详情/弹窗…） | 菜单说明的一部分 | 菜单内切换功能点时**右侧说明不动** |

**反例（禁止）**：① 每个菜单各生成一份 index.html；② 每个功能点各自配一份说明；③ 把某功能点的说明挪进它对应的页面区域。

**技术实现要点（多菜单单文件）**：
- 右侧说明区按菜单分 pane：`<div class="menu-pane" data-menu="clue" data-label="线索管理">`，非当前菜单加 `hidden`
- 菜单切换：Vue `switchMenu(m)` 同时改左侧，并调 `window.showMenuPane(m)` 切右侧 pane；当前菜单记在 `<body data-active-menu>`
- 编号气泡：各菜单独立从 ① 编号；`flashAll()` 用 `offsetParent` 过滤，只点亮当前可见 pane 内元素
- localStorage 一个 key 存全部 pane；导出 Markdown（Agent 侧 `--to-md`）按 pane 的 `data-label` 分 `# 菜单名` 大节
- 未实现的菜单项置灰，点击 toast「该菜单暂无原型，需求评审后再补」

### 3.1 说明只有两章

| 章节 | 内容 |
|---|---|
| **一、页面概述** | 菜单位置 · 解决问题 · **权限说明表** |
| **二、功能说明** | 按功能点逐个展开，每个功能点一张卡片 |

> 原「字段 / 元素说明表」「业务规则与异常态」两章**已取消**：字段表并入各表单/列表/详情功能点，业务规则并入各功能点内部。不再有全局字段表。

### 3.2 一、页面概述

1. **菜单位置**（可编辑）
2. **解决问题**（可编辑）
3. **权限说明**（表格）—— 原「页面构成」行改为本表；**「使用角色」行已删除**

| 列 | 表头 | 内容 | 编辑权限 |
|---|---|---|---|
| 1 | 功能点 🔒 | 本菜单全部功能点（如：线索列表、录入线索、编辑线索、删除线索、线索详情） | **不可修改**，与左侧原型强绑定，不可增删行 |
| 2 | 操作权限 ✏ | 使用该功能的角色 | 可修改 |
| 3 | 数据权限 ✏ | 一般**只有列表类功能**才有；其余功能该列留空 | 可修改 |
| 4 | 备注 ✏ | 默认留空 | 可修改 |

> **⚠️ 强制：第 2/3/4 列一律初始留空，不得替用户预填内容（2026-10-08 用户拍板）**
> 角色分工、数据可见范围属于用户侧业务口径，需求没提就**不许脑补**（曾被否过的反例：「销售代表、销售经理」「销售经理可删除」这类默认值）。
> 生成时这三列写成空单元格 `<td data-edit></td>`，保持可编辑，由用户在浏览器中填写。
> 空单元格须有占位提示（`.spec-tb td[data-edit]:empty::after{content:"点击填写"}`）并设 `min-height:24px`，保证点得到。

### 3.3 二、功能说明

**每个功能点 = 一张卡片**：编号 ① ② ③… + 功能点名称。**不显示类型标签**（v3.1 用户要求删除「列表类/表单类」等标签；类型只用于决定子项结构，不再可视化）。
- 功能点清单 = 权限说明表第 1 列，**锁定、不可增删**（要补内容用工具条「+ 新增章节」自建）
- 编号单位 = **功能点**（不再是"交互步骤"），各菜单独立从 ① 排

#### 2.1 列表类功能（如「线索列表」）
> 即使点开菜单默认就是列表，也必须把列表当成一个独立功能点写。

| 子项 | 写法 | 编辑 |
|---|---|---|
| **交互** | 简略写：触发 → 行为 → 反馈（筛选、重置、翻页可合并成一条） | 可改 |
| **状态流转说明** | 写法：`A状态：当 xxx 时，数据由 A 状态变为 B状态；` 逐状态列举。**原型里没有状态变更入口 → 一律留空**（2026-10-08 用户拍板），由用户填 | 可改 |
| **列表字段** | 表格：元素 🔒 ｜ 展示逻辑说明 ✏ ｜ 备注 ✏ | 第 1 列锁定，2/3 列可改 |
| **数据排序规则** | 写查询结果的排序（按哪个字段、正序/倒序） | 可改 |

- 「展示逻辑说明」写：时间展示到秒、状态渲染成彩色标签、超长截断、可点击跳转等
- **「操作」也算一列**：展示逻辑说明填 `/`，备注写「xx 状态下的数据展示 xx 按钮」

#### 2.2 表单类功能（如「录入线索」「编辑线索」）

| 子项 | 写法 | 编辑 |
|---|---|---|
| **交互** | 简略写，并**写明是页面还是弹窗**（如：点「录入线索」→ 弹出「录入线索」弹窗，非独立页面） | 可改 |
| **字段说明** | 表格：元素 🔒 ｜ 类型 🔒 ｜ 必填 ｜ 校验规则 ｜ 默认值 ｜ 备注 | **列权限分两种**（见下）；不支持增删行、列 |
| **业务规则说明** | 提交校验（非空、格式、唯一性判重等）；**分条展示，每条一个圆点行**（`.rules`），禁止写成一段话；没有则留空但**保留该条** | 可改 |

- **字段说明列权限（v3.1 用户规定）**：
  - **新增类表单**（录入/新增 xx）→ 仅「备注」列可改，必填/校验规则/默认值仍锁定
  - **编辑类表单**（编辑 xx）→ 「必填 / 校验规则 / 默认值 / 备注」四列可改，仅元素与类型两列锁定
- 编辑类表单中「回显但不可编辑」的字段 → 写进**备注列**；默认值列对编辑态写「回显当前值」

#### 2.3 详情类功能（只展示不可编辑，如「线索详情」）

| 子项 | 写法 | 编辑 |
|---|---|---|
| **交互** | 简略写，写明跳转的是页面还是弹窗 | 可改 |
| **展示元素说明** | 表格：分组 🔒 ｜ 字段名 🔒 ｜ 展示逻辑说明 ✏ ｜ 备注 ✏ | 分组名与字段名锁定，其余可改 |

- 详情页字段分组展示时，表格**按分组逐行写**；无分组时去掉「分组」列
- 页面头部（名称/状态/次要信息/右上按钮）也作为一个分组写进去

#### 2.4 可视化类功能（数据看板：柱状图/饼图/折线图/雷达图）

| 子项 | 写法 | 编辑 |
|---|---|---|
| **交互** | 点击 xx 后展示 xx，简写 | 可改 |
| **数据逻辑** | **重点**：逐个指标写清计算口径/公式（增长率 = (本期-上期)/上期 × 100%）；不确定就留空让用户自己填 | 可改 |

#### 2.5 其他类功能（单个动作，如删除、更新、启用/停用）

| 子项 | 写法 | 编辑 |
|---|---|---|
| **交互** | 点击 xx 后展示 xx，简写 | 可改 |
| **业务规则说明** | 写校验规则（如删除前校验 xx）；**分条展示，每条一个圆点行**，禁止写成一段话 | 可改 |

### 3.4 编号气泡联动（v3.0 调整）

- **一个功能点 = 一个编号**：列表类的筛选卡、分页器挂同一编号；表单/详情/其他类的按钮、⋯ 下拉项、详情页右上按钮挂同一编号
- **点左侧编号气泡 → 右侧自动平滑滚动到该编号对应的功能点卡片**（`scrollIntoView({behavior:'smooth',block:'center'})`，在当前可见 pane 内查找 `.fn.item[data-k=k]`），再双向高亮
- **点右侧功能点卡片不滚动**（避免自身跳动）—— 卡片 `onclick` 调 `flashAllNoScroll(k)`，即 `flashAll(k,{noScroll:true})`
- 点击任一侧可定位并高亮另一侧；纯规则类不再单独编号（已并入功能点内部）
- 气泡挂在**内容区控件**上，不挂菜单/顶栏这类框架元素

### 3.5 编辑权限总表（白/黑名单）

| 区域 | 可改 | 锁定 |
|---|---|---|
| 菜单位置 / 解决问题 | ✅ | — |
| 权限说明表 | 操作权限、数据权限、备注三列 | 功能点列（含行不可增删） |
| 功能点名称 | ❌ | 与原型强绑定，卡片不可增删；**不显示类型标签**（v3.1） |
| 各功能点的「交互」「状态流转」「数据排序」「业务规则」「数据逻辑」 | ✅ | — |
| 列表字段表 | 展示逻辑说明、备注 | 元素列（含行不可增删） |
| 表单字段说明表（**新增类**） | 仅备注列 | 元素/类型/必填/校验规则/默认值；表不可增删行/列 |
| 表单字段说明表（**编辑类**，v3.1） | 必填、校验规则、默认值、备注四列 | 仅元素与类型两列；表不可增删行/列 |
| 详情展示元素表 | 展示逻辑说明、备注 | 分组、字段名 |
| 自定义章节（+ 新增章节，v3.1） | ✅ 文字可改；**每个章节带独立「删除章节」按钮**（点击需 confirm），不依赖编辑模式 | — |

## 四、硬约束（生成时必须遵守）

1. **只实现需求文档中提到的功能，禁止自由发挥添加新需求**（v1 试跑自行加统计卡/批量导入/导出/超时提醒——已被此条叫停）
2. 需求模糊时先追问，不脑补业务规则（状态流转、数据权限口径若需求未提，对应条目**留空**交给用户填，不编造）
3. mock 数据必须贴近真实中文业务场景但全部虚构：虚构的姓名、公司名，手机号用 `138 0000 xxxx` 这类明显虚构的号段；不得使用真实存在的企业名称和真实手机号；禁止 lorem /「示例文本」
4. **确认粒度：复杂需求才先出页面结构清单确认**（多页面/含流程流转时）；单页面简单需求直接生成
5. **【迭代默认】用户未特殊说明时，新增需求一律归入已存在的同一个原型文件**——**默认「改」，不是「建」**
   - **判定归属**：新需求所属菜单属于同一系统（同一产品/同一套菜单体系）→ 打开该系统已有的 index.html 追加
   - **只有以下情况才新建文件**：用户明确说「新建一个原型/另一个系统/另一个项目的原型」
   - **拿不准就问**：「这个需求是加到 <已有系统名> 里，还是另起一个新系统？」
   - **默认只做加法**：追加菜单项、内容区页面、说明 pane；用户没有明确要求时不删除、不重写已有菜单与说明，不擅改已验收功能；用户要求的删改照做，并写进更新摘要
   - 追加顺序：新菜单加 nav 末尾、新 pane 加 `#specBody` 末尾
6. **说明结构变更时必须换 `PROTO_KEY`**（否则用户浏览器里的旧缓存会覆盖新结构，看起来像没生效）
7. **【v3.7】原型动了，说明必须跟着动**：优化需求一旦改了左侧原型（加菜单 / 加页面或弹窗 / 加字段或列表列 / 改交互形态 / 加状态 / 改筛选排序），右侧说明必须**在同一次交付里同步更新**。
   - 逐项对照表见 `add-menu-checklist.md` 第 0 节「原型改动 → 说明同步对照表」
   - **交付时必须给出概括性的「本次需求说明更新摘要」**：按菜单分组、每条一句话说清改了哪个功能点的什么；单列一条"左侧原型同步改动"；提醒新增内容里仍留空待填的项（权限三列 / 状态流转 / 公式）
   - 交付「原型变了但说明没跟」的原型 = 半成品，禁止

## 五、交付物

| 项 | 规范 |
|---|---|
| 格式 | 单个 `index.html`（HeroUI 样式、Tailwind、Vue 走 CDN，lucide 图标内联，其余零本地依赖） |
| 目录 | `<原型目录>/<系统名>/index.html`（**一个系统一个目录一份文件**；`<原型目录>` 的确定方式见 `SKILL.md`「原型目录」） |

| 打开方式 | 双击浏览器打开；交付时给出文件的绝对路径，运行环境有浏览器自动化工具时自己打开并用 DOM 快照检查 |
| **迭代模式（默认）** | 后续新需求**默认修改同一份 index.html**，不新建文件 |

## 六、界面样式：HeroUI 组件 + lucide 图标

### 6.1 样式来源
- 组件外观：`https://cdn.jsdelivr.net/npm/@heroui/styles@3.2.6/dist/heroui.min.css`（HeroUI v3 官方编译样式，Apache 2.0）。它靠 `块__元素--修饰` 类名和少量状态属性出样式，不依赖 React
- 布局：Tailwind v4 浏览器版只写 flex、grid、间距、宽高；颜色、圆角、阴影用模板 `<style type="text/tailwindcss">` 里接好的主题工具类：`bg-background`、`bg-surface`、`bg-surface-secondary`、`text-foreground`、`text-muted`、`border-border`、`border-separator`、`bg-default`、`text-accent`、`shadow-surface`、`shadow-overlay`
- **禁止**：写死颜色值（`#2563EB`、`bg-slate-*`、`bg-blue-*` 这类）、写死 11px / 12px 字号（用 `text-xs` / `text-sm`，对应 HeroUI 的 `--text-xs` / `--text-sm`）、用 Tailwind 自己拼按钮和输入框
- 主色、成功、警示、危险用 HeroUI 的 `accent`、`success`、`warning`、`danger`；状态标签用 `chip chip--soft chip--sm` 加颜色变体（`chip--success`、`chip--warning`、`chip--danger`、`chip--accent`、`chip--default`）

### 6.3 状态属性（HeroUI 读这些属性，不读原生 :checked 等；模板组件已处理，自己写结构时照做）

| 组件 | 状态 |
|---|---|
| 复选框 | 选中 `data-selected="true"`，半选 `data-indeterminate="true"`；勾的 SVG `stroke-dashoffset` 选中 44、未选中 66 |
| 单选框 | 用隐藏的原生 `<input type="radio">`，HeroUI 认 `:has(input:checked)`；`radio__indicator` 里不能有任何字符 |

| 下拉框 | 打开时箭头写 `data-open="true"`，没选值时 `select__value` 写 `data-empty="true"`；选中项 `data-selected="true"`；弹层位置自己算（`position:fixed` + `--trigger-width`） |

## 七·补、右侧说明的在线编辑能力

**持久化方案：A（改动自动存 localStorage + 导出按钮）**；保留 CDN，不强求离线。

### 实现约束（避免踩坑，必须遵守）

1. **右侧说明区用静态 DOM，不被 Vue 托管** —— 否则导出后再次打开，Vue 重新渲染会覆盖用户编辑
2. **唯一缓存 key** —— 每个文件一个 key；导出时生成新 key 写入导出文件，避免各版本串味
3. **导出 HTML** —— 序列化 `documentElement.outerHTML` + 新 key，下载后仍可继续编辑、继续导出（链式迭代）。序列化前在 `#specBody` 上写 `data-base-key`＝当前文件的 `PROTO_KEY`；`#specBody` 上已有这个属性（当前打开的就是导出文件）时保留原值，使它始终指向用户最初打开的原型文件的 key，供合并时判断目标文件在导出之后有没有被改过
4. **导出 Markdown —— 按钮已删除（v3.8），改由 Agent 侧生成**：用户要 md 时跑 `node <skill>/scripts/edit-spec.js <index.html> --to-md`，输出到原型同目录的 `<模块名>-需求说明-<时间戳>.md`，按 `# 菜单名` → `## 章节` → `### 编号 功能点` → 子项（含表格 / 分条规则）输出。
   - 删除原因：md 只出不进（改了 md Agent 看不到），不在「浏览器改 → 导出 HTML → 回传」主链路上；摆在主工具条上还会让人误以为它也能回传
   - **页面上的按钮不许再加回来**
5. **导出文件名不写死** —— `<模块名>-原型-YYYYMMDD-HHMMSS.html` / `<模块名>-需求说明-YYYYMMDD-HHMMSS.md`；模块名取自 `<body data-module="...">`
6. **恢复默认** —— 一键清缓存回到生成时的初始说明
7. 编号联动在编辑后仍可用（`data-k` 不因编辑丢失）；右侧卡片的点击只由卡片自己的 `onclick="flashAllNoScroll(k)"` 处理，不加 document 级的 `.item` 点击监听
8. **工具条位置（v3.2）**：吸附在**右侧说明区底部** —— `<div id="toolbar" class="sticky bottom-0 z-20 …">`，放在 `</aside>` 之前、**`#specBody` 之后**（必须在容器外，否则会被 localStorage 存进去导致重复渲染）。按钮：编辑需求说明 ｜ 新增章节 ｜ 导出 HTML ｜ 导出给 AI ｜ 恢复默认（「新增表格段落」「导出 Markdown」两个按钮均已删除，后者改由 Agent 侧 `--to-md` 生成）
9. **顶部提示框**：说明区顶部一条 HeroUI 警示提示条（`alert alert--warning`，标题「怎么看这份说明」），按行分条展示（每行一个 `<div>`），禁止挤成一段：
   - 右侧说明跟随左侧菜单切换：一个菜单一份完整说明，菜单内切换页面 / 弹窗时说明不变。
   - 点「编辑需求说明」可直接改（自动保存到本机浏览器）；
   - 点编号气泡后可定位到具体的功能描述，编号不是具体的功能需求，是功能编号；
   - 带 🔒 的列与左侧原型强绑定，不可修改。
   - 改动只存在本机浏览器缓存里，Agent 看不到。改完请点底部「导出 HTML」，再把导出的文件交给 Agent 合并。（用虚线与其上内容分隔，防断层）
10. **业务规则展示（v3.1）**：业务规则的多条内容必须**分条展示**——容器加 `class="sub-v rules"`，CSS 给每条加圆点（`.rules > div::before{content:"•"}`）+ 行距，禁止写成一段话。Markdown 导出时按子列表（`  - `）输出。

### 列级锁定实现
- 锁定单元格：`<td class="lock">`（无 `data-edit`，编辑态不变黄）
- 可编辑单元格：`<td data-edit>`（编辑态黄虚线框 + contenteditable）
- 表格禁止增删行：不加 `data-editable-table` 属性即可（页面上没有「新增表格段落」入口；历史导出文件里若存在自定义表格段落，模板里的 `addRow` / `delRow` / `delSection` 保留以兼容）

### 七·补2、Agent 同步的断层与「方案 A 回传」（2026-10-08 确立）

#### 断层真因：说明有两个真相源

| 真相源 | 谁能改 | Agent 能看到吗 |
|---|---|---|
| 磁盘上的 `index.html` | Agent | ✅ |
| 浏览器缓存 | 用户 | ❌ |

**浏览器 `file://` 页面对本机磁盘只有读权限**——浏览器把 HTML 读进内存生成 DOM 副本，用户改的是内存副本，禁止写回源文件。这是安全模型的硬边界：否则任何下载来的 HTML 双击后都能篡改硬盘。

**四条看似可行的路，全部堵死**：
| 招数 | 死因 |
|---|---|
| File System Access API | Chrome 禁止 `file://` 下调用，必须 https/localhost |
| fetch / AJAX 写文件 | HTTP 无写文件语义；file:// 下 origin 为 null，CORS 拦死 |
| ActiveX / FileSystemObject | 随 IE 淘汰 |
| Electron 打包 | 能写，但违背「零安装、双击即开」 |

所以结论是二选一：**要双击即开 → 只能导出回传（方案 A）；要自动直写 → 必须放弃双击即开（方案 B，需起本地服务 + 每次授权）**。当前选 **A**。

**方案 B 的重要澄清**：B 只解决"同步"，**不解决"覆盖"**——Agent 重新生成说明时照样会整体覆盖用户改动。所以 `data-user-edited` 定稿标记是 A 和 B **都必须**做的。

#### 方案 A 落地链路

1. **用户**：浏览器里改（新增章节 / 改单元格）→ 自动存缓存 → 点「导出 HTML」→ 得到一个 `系统名-原型-时间戳.html`
2. **用户**：把文件路径告诉 Agent
3. **Agent**：先干跑 `node scripts/merge-spec.js <导出文件> <目标index.html> --dry-run`，确认无异常后去掉参数执行
4. **脚本**：危险内容检查 → 缺失检查 → 导出后改动检查 → 备份原文件到 `_archive/` → 只替换 `#specBody`（左侧原型一字不动）→ 换新 `PROTO_KEY` → 输出差异报告
5. **后续**：带 `data-user-edited` 标记的内容视为用户定稿，Agent 不得覆盖

#### 人工定稿标记机制

- `onEdit` 里取 `e.target.closest('[data-edit]')`，给它打 `data-user-edited="1"`
- `addSection` 新建的章节，整块 `[data-edit]` 一律打标
- 标记随 `innerHTML` 序列化导出，是 Agent 识别"用户改过"的**唯一依据**
- **Agent 迭代铁律**：要改的目标单元格若已带该标记 → 保留原文，把冲突点列给用户决定，禁止自行改写

#### 脚本 merge-spec.js

```
node <skill>/scripts/merge-spec.js <导出的 html> <目标 index.html> [--dry-run] [--force]
```

| 能力 | 说明 |
|---|---|
| 精确替换 | 用 div 深度配平定位 `#specBody`，只换说明区；写入时去掉 `data-base-key` |
| 危险内容检查 | 来源说明区出现 `<script>`、`<iframe>`、`<object>`、`<embed>`、`javascript:`，或白名单（`flashAllNoScroll('…')`、`delSection(this)`、`addRow(this)`、`delRow(this)`）之外的 `on*=` 事件属性 → **中止**，`--force` 也不放行 |
| 缺失检查 | 目标有、来源没有的菜单/功能点（按「菜单 id + 编号 + 名称」比对）→ 判定「用户基于旧版修改」，默认**中止**并提示重改或 `--force` |
| 导出后改动检查 | 来源的 `data-base-key` 与目标当前的 `PROTO_KEY` 不一致 → 目标在导出之后被改过，列出目标里带 `data-agent-edited`、来源里找不到相同文字的单元格（合并会冲掉它们），默认**中止**；来源没有 `data-base-key`（旧版模板导出）时只在有这类单元格时中止 |
| 自动备份 | 写入前备份到 `<目标目录>/_archive/index-before-merge-<时间戳>.html`，同类备份只留最近 20 份 |
| 换 key | 生成新 `PROTO_KEY`，防止浏览器旧缓存盖回写入结果 |
| 差异报告 | 菜单清单、自定义章节数、人工标记数、说明区体积变化 |

### 七·补3、需求说明显隐开关（v3.5）

**需求**：左侧原型区右下角放一个开关，点一下隐藏右侧说明、再点一下显示；隐藏时左侧原型铺满全屏。

**DOM 结构（必须这样包一层）**
```html
<div id="protoWrap" class="relative shrink-0">
  <div id="app" v-cloak class="p-4"></div>
  <button id="specToggle" type="button" class="button button--secondary button--sm" onclick="toggleSpec()" title="显示 / 隐藏右侧需求说明">
    两个 lucide 图标（data-icon="hide" / "show"，按状态切换显示）+ <span id="specToggleText">隐藏需求说明</span>
  </button>
</div>
```
- 分割线加 `id="specDivider"`，右侧 aside 加 `id="specAside"`
- **开关必须放在 `#protoWrap` 内、`#app` 之外**：放进 `#app` 会被 Vue 渲染模板时覆盖掉；放进 `#specBody` 会被 localStorage 存进去导致重复渲染

**CSS（宽度不要用 Tailwind class 写死在 `#app` 上，否则切不动）**
```css
#protoWrap{width:62%}
body[data-spec="hidden"] #protoWrap{width:100%}
body[data-spec="hidden"] #specDivider,
body[data-spec="hidden"] #specAside{display:none}
#specToggle{position:absolute;right:20px;bottom:20px;z-index:40;box-shadow:var(--overlay-shadow)}
```

**状态与持久化**
- 状态记在 `<body data-spec="shown|hidden">`（导出 HTML 时会随 DOM 带走 → 导出文件保持导出时的显隐状态）
- 缓存 key = `PROTO_KEY + ':hidden'`，与说明内容共用一套 key 前缀，换 key 后自然失效
- 读取优先级：**缓存有值用缓存** → 否则沿用 body 自带的 `data-spec`（兼容导出文件）→ 否则默认 shown
- 按钮随状态变：显示态「收起面板」图标 +「隐藏需求说明」／隐藏态「展开面板」图标 +「需求说明」（只改 `#specToggleText` 的文字和两个图标的显隐，不要用 textContent 整个覆盖按钮）

**联动**：`flashAll()` 开头检测 `data-spec==='hidden'` → 自动调 `setSpecHidden(false)` 先展开再滚动定位。否则说明隐藏时点编号气泡会毫无反应。

**已知取舍**：开关是悬浮按钮，可能轻微压住列表页右下角的分页；若用户反馈遮挡，改 `right`/`bottom` 值或改为左下角。

### 七·补4、对话式修改需求说明（场景 C，v3.6）

> 与场景 B 的区别：**B 是用户改完回传给 Agent（改在浏览器里发生）；C 是用户直接让 Agent 改（改在磁盘文件里发生）。**

#### 三条铁律

1. **默认只改 `#specBody`，左侧原型（`protoTpl` / `#app` / 脚本）一字不动** —— 除非用户明确说"原型也一起改"
2. **改动若与原型强绑定 → 先确认再动手**（判定表见下）
3. **改完必换 `PROTO_KEY`**，否则用户浏览器旧缓存会把改动盖回去

#### 一致性判定表、执行顺序与冲突预检

以 `SKILL.md`「对话修改需求说明流程（场景 C）」为准，本规范不重复。要点：先冲突预检，再 `--list` 定位、过一致性判定，**改内容之前**跑 `--bump-key`，改完跑 `--verify`。

`--verify` 只拿最近一次 `--bump-key` 留下的 `index-before-edit-*.html` 当基线，检查四项：protoTpl 未变、脚本未变（**排除 PROTO_KEY**，否则必假报）、🔒 锁定单元格文本集合未变、人工定稿标记未减少。退出码非 0 = 有项需要人工确认。

多行替换匹配失败时：先 `node edit-spec.js <index.html> --norm` 把 CRLF 归一成 LF（会先备份），再替换。

#### 说明区的写法要求

脚本用正则读取说明区，Agent 手工改说明时保持模板里的写法，否则 `--list`、`--verify`、`--to-md`、`--check` 会漏项：
- 子项写成一行 `<div class="sub"><div class="sub-k">子项名</div><div class="sub-v" …>内容</div></div>`，`sub`、`sub-k`、`sub-v` 三个标签之间不加换行
- `menu-pane` 的属性顺序保持 `class`、`data-menu`、`data-label`
- 功能点卡片写成 `<div class="fn item" data-k="①" …>`，`class` 和 `data-k` 在前，名称放在 `<span class="fn-name">` 里

#### 标记体系

| 标记 | 谁打的 | 含义 | 优先级 |
|---|---|---|---|
| `data-user-edited="1"` | 浏览器 `onEdit` / `addSection` | 用户在浏览器里定稿 | **最高，Agent 不得覆盖** |
| `data-agent-edited="1"` | Agent 场景 C 改写时手动加 | Agent 改过 | 低于用户标记 |

两个标记共存 = "Agent 写过、用户又改过" → 以用户内容为准。

### 七·补5、导出需求说明 Markdown（场景 D，v3.9）

> 页面上的「导出 Markdown」按钮已在 v3.8 删除，改由 **Agent 侧**生成。这是**独立触发场景**，不是场景 C 的附属动作。

判定和步骤（冲突预检 → `--to-md` 生成 → 给出 md 的绝对路径）以 `SKILL.md`「导出需求说明 Markdown（场景 D）」为准，本规范只写输出规格。

**输出规格**
- 文件名：`<模块名>-需求说明-<时间戳>.md`，写在原型同目录
- 结构：`# 需求说明` → `# 菜单名`（按 `.menu-pane` 的 `data-label`）→ `## 章节`（section 的 h3）→ `### 编号 功能点` → 子项
- 子项三种形态：含表格 → Markdown 表格；业务规则（`.rules`）→ `  - ` 子列表；空 → 「（待补充）」

**红线**：**不许**为这个需求在页面上加回「导出 Markdown」按钮（v3.8 已删，理由见七·补第 4 条）。

### 七·补6、导出给 AI

**需求**：用户拿原型去让 Claude Code 或 Codex 实现需求时，需要一段说清「要做什么、不能做什么」的提示词。

**入口与形式**：工具条「导出给 AI」→ 弹窗（静态 DOM `#aiPromptModal`，在 `#specBody` 之外，不随说明保存），弹窗里是只读文本框，按钮「复制」「下载 .md」，Esc 或点遮罩关闭
- 复制：用剪贴板接口；浏览器不允许时选中全文、提示用户按 Ctrl+C，并写明原因
- 下载：文件名 `<模块名>-AI提示词-YYYYMMDD-HHMMSS.md`

**内容**（`aiPrompt()` 从当前说明区的 DOM 生成，所以包含用户在浏览器里改过的内容）：
1. `# 需求：<模块名>`，说明这份需求来自原型 HTML，原型文件会一起给 AI
2. 「必须遵守」：只实现说明里写到的功能；标为「未提供，需确认」的不要自己补，先问；原型里的示例数据、颜色和组件只是示意，以项目现有代码和规范为准；不确定先问，不要猜；动手前先说明要改哪些文件
3. 每个菜单一节：页面概述的子项、权限说明表，然后每个功能点（编号 + 名称）的交互、字段表、业务规则等子项
4. 表格转 Markdown 表格（表头去掉 🔒 ✏）；业务规则转分条；**任何空的子项、空单元格都写「未提供，需确认」**；用户新增的章节照样输出

**和其他导出的关系**：只出不进，不参与「导出 HTML → 合并」链路；不改说明内容、不换 key。
