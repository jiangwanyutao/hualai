# 业务需求原型生成（page-prd）

把业务需求变成一份**可点、可读、可改**的单文件原型：**左边是功能页面，右边是需求说明**。

## 原型目录

原型放在「原型目录」下，一个系统一个子目录：`<原型目录>/<系统名>/index.html`。

- 用户指定了目录就用用户指定的
- 没指定时用 `<当前工作目录>/prototypes/`
- 当前工作目录下没有 `prototypes/`、对话里也没提过原型位置时，先问用户原型放在哪，再继续

下文的 `<原型目录>` 都指这个目录，`<skill>` 指本 skill 所在目录。

## 用命令调用时

用户输入 `/hualai:page-prd …` 时，命令后面的内容在本文件末尾的 `<args>` 里，按下方「何时触发」判断是哪个场景：是需求描述就走场景 A；是 `*-原型-YYYYMMDD-HHMMSS.html` 路径就走场景 B；是要改说明的内容就走场景 C；要导出说明 Markdown 就走场景 D。`<args>` 为空时，先问用户要做什么原型、或要对哪份原型做什么。

## 何时触发

**场景 A — 生成 / 迭代原型**（最常见）
用户说：帮我绘制/生成 XX 的原型、给 XX 系统做个原型、把 XX 需求画成原型、给已有原型加个 XX 菜单/功能。默认 PC 端后台系统。
→ 走下方「执行流程」。

**场景 B — 人工修改回传**（用户在浏览器里自己改过需求说明之后）
用户说：我在页面上改好了 / 导出文件在 xxx / 帮我把浏览器里改的说明合并一下；或直接甩过来一个 `*-原型-YYYYMMDD-HHMMSS.html` 路径。
→ **直接跳到下方「人工修改回传流程」**。此场景**严禁重新生成原型**——重生成会把用户改的说明整块冲掉。

**识别场景 B 的信号**（出现任一就先确认是不是回传，别一上来就生成）：
1. 给的文件名符合导出格式 `<模块名>-原型-YYYYMMDD-HHMMSS.html`
2. 提到「导出」「缓存」「我在页面上改了」「浏览器里改的」
3. 提到把浏览器里的改动「合并」「回传」

**场景 C — 对话修改需求说明**（用户直接说要改说明内容，不经过浏览器）
用户说：帮我改下原型的需求说明里的 xxx / 说明里「xx」那段改成 xxx / 权限表补一下角色 / 业务规则再补一条 / 状态流转填一下。
→ **默认只改右侧说明，左侧原型一字不动**（详见下方「对话修改需求说明流程（场景 C）」）。

**识别场景 C 的信号**：要改的是本 skill 生成的原型的右侧说明（用户给了原型的 `index.html`，或对话里、`<原型目录>` 下已有这份原型），且没提浏览器导出。

**场景 D — 导出需求说明文本**（用户要拿走说明，不改任何东西）
用户说：把原型的需求说明导出成 Markdown / 我要把原型说明发给开发 / 帮我导一份说明出来贴文档里。
→ 跑 `edit-spec.js --to-md` 生成 `<模块名>-需求说明-<时间戳>.md`，**原型文件与说明内容一律不动**，然后把文件给用户（详见下方「导出需求说明 Markdown（场景 D）」）。

**四个场景的判定顺序**：
1. 给了导出格式的文件（`*-原型-YYYYMMDD-HHMMSS.html`），或说在浏览器里改过、要合并 → B
2. 给的是原型的 `index.html` 路径或没给路径时，按用户要做的事判断：加菜单、加功能、新做原型 → A；**改**说明内容 → C；**导出/拿走**说明文本 → D

C 与 D 的关键区别：C 是"改内容"，D 是"只导出副本、不改任何东西"。
**拿不准就问一句**：「你是想新生成一版、把你在浏览器里改的说明合并回来、让我直接帮你改说明内容，还是只要一份 Markdown 文本？」

## 产物形态（一句话）

```
[ 左 62%：B 端后台系统原型 ] │分割线│ [ 右 38%：该菜单的需求说明 ]
   左侧菜单 + 内容主区            竖排       两章式 + 编号联动
                                 虚线+黑字   一、页面概述（含权限说明表）
                                             二、功能说明（按功能点展开）
```

**右侧说明的两章结构**
- 一、页面概述：菜单位置 · 解决问题 · **权限说明表**（功能点🔒 / 操作权限✏ / 数据权限✏ / 备注✏；后三列初始留空）
- 二、功能说明：**一个功能点 = 一张编号卡片**（编号 + 名称，**不显示类型标签**），按类型写子项
  - 列表类：交互 → 状态流转（无则留空）→ 列表字段表 → 数据排序规则
  - 表单类：交互（页面 or 弹窗）→ 字段说明表（**新增类仅备注可改；编辑类必填/校验规则/默认值/备注四列可改**）→ 业务规则说明（**分条圆点展示，禁止一段话**）
  - 详情类：交互 → 展示元素说明表（分组/字段名锁定）
  - 可视化类：交互 → 数据逻辑（每个指标的计算公式）
  - 其他类：交互 → 业务规则说明（分条圆点展示）
- 顶部提示框：**警示色分行展示**（跟随菜单切换 / 可编辑自动保存 / 编号双向定位 / 🔒 列不可改 / 改完导出交给 Agent）
- **显隐开关**：左侧原型区右下角悬浮按钮，控制右侧说明显示/隐藏；隐藏时左侧铺满全屏
- 工具条（**吸附在右侧说明区底部**，sticky）：**编辑需求说明** ｜ **+ 新增章节**（可单个删除，带 confirm）｜ 导出 HTML ｜ **导出给 AI** ｜ 恢复默认。页面上没有「导出 Markdown」按钮——md 只出不进，不在回传链路上；需要 md 时用 `edit-spec.js --to-md` 由 Agent 生成
- **导出给 AI**：把当前说明区（含用户在浏览器里改过的内容）整理成给 Claude Code / Codex 的提示词，弹窗里可复制、可下载 `<模块名>-AI提示词-<时间戳>.md`；留空项写「未提供，需确认」，并要求 AI 只做说明里写到的、不确定先问。用户说「生成给 AI 的提示词」「让 Codex 按原型实现」时，请他打开原型点这个按钮
- **界面样式**：左侧原型和右侧说明都用 HeroUI 官方编译样式（`heroui.min.css`）的组件类名和主题变量，Tailwind v4 浏览器版只负责布局；图标一律用 lucide 内联 SVG（模板里的 `ICONS` 和 `<lc-icon>`），禁止用 emoji 当图标

**完整规范见 `references/prototype-spec.md`（必读，含全部技术细节与禁忌）。**

## 执行流程

0. **先确认没有未回传的人工修改**（用户若提到上次在浏览器里改过，或直接给了导出文件路径，跳到「人工修改回传流程」）
1. **判定归属（第一步必做）**
   - 先看 `<原型目录>` 下有没有同源系统的 index.html
   - **默认「改」不是「建」**：用户没说新建 → 在已有文件上追加；只有用户明确说「新建另一个系统/项目的原型」才新建目录
   - 拿不准就问，禁止凭感觉新建
2. **复杂需求先出结构清单**（页面 + 区块/字段 + 哪些做弹窗 + 本次是新增菜单还是菜单内加页面），简单需求跳过
3. **生成文件**：
   - 首次 → 复制 `assets/template.html` 到 `<原型目录>/<系统名>/index.html`，改造成目标系统（替换系统名、菜单项、mock 数据、说明 pane）
   - 迭代 → 在已有 index.html 上修改（详见 `references/add-menu-checklist.md`）
   - **原型动了说明必须跟着动**：照 `add-menu-checklist.md` 第 0 节的「原型改动 → 说明同步对照表」逐项补右侧，禁止交付"原型变了但说明没跟"的半成品
4. **自检**（别省）：`node "<skill>/scripts/edit-spec.js" <index.html> --check`，退出码非 0 时按输出修好再跑；再按 `add-menu-checklist.md` C 节逐项人工确认（未实现的功能没被偷偷做进去等）
5. **交付**：给出 index.html 的绝对路径，请用户双击用浏览器打开；运行环境有浏览器自动化工具（如 Playwright MCP）时，自己打开页面，用 DOM 快照走一遍菜单切换和编号联动。同时给出「本次需求说明更新摘要」：按菜单分组、每条一句话说清改了哪个功能点的什么；单列一条"左侧原型同步改动"；提醒新增内容里仍留空待填的项（见 `add-menu-checklist.md` F 节）

## 不能碰的红线

1. **只用需求文档里提到的功能**，禁止自由发挥（例：客户管理没提删除，就真的不做删除）
2. **一个系统 = 一个 index.html**，所有菜单在同一文件里切换；新增说明随菜单联动
3. **默认迭代同一文件**，不新建；用户没有明确要求时，不删除、不重写已有菜单与说明；用户要求的删改照做，并写进更新摘要
4. **mock 数据贴近真实格式但必须虚构**：虚构的中文公司名、姓名，手机号用 `138 0000 xxxx` 这类明显虚构的号段；不得使用真实存在的企业名称和真实手机号；禁止 lorem、禁止「示例文本」
5. **导出文件名带时间戳**（`模块名-原型-YYYYMMDD-HHMMSS.html`），禁止写死
6. **说明表里的用户口径一律留空**：
   - 权限说明表的**操作权限 / 数据权限 / 备注**三列 → 初始必须为空单元格，禁止预填「销售代表、销售经理」这类角色默认值
   - **状态流转说明** → 原型里没有状态变更入口就留空
   - 可视化类的**数据逻辑公式**、不确定口径同理留空
   - 这些属于用户业务口径，需求没提就不许脑补；留空但仍保持可编辑（`data-edit`）
7. **需求没提的不编造**：数据权限口径、指标公式若需求未定义 → 对应条目**留空**交给用户填
8. **说明结构/内容变更时必须换 `PROTO_KEY`**，否则用户浏览器里的旧缓存会覆盖新内容
9. **不许覆盖用户的定稿**：改说明前先检查目标单元格有没有 `data-user-edited`。有 → 保留原文，把冲突点列给用户让他决定，禁止自行改写
10. **场景 C 默认只改说明、不动原型**；改动若命中「一致性判定表」里的 ✅ 项（功能点增删、字段名/元素列、交互形态、状态/筛选/排序变化）→ **必须先问用户要不要同步改原型**。禁止擅自改原型，也禁止偷偷把说明改成原型上没有的样子
11. **原型动了，说明必须跟着动**：优化需求一旦改了左侧原型（加菜单/加页面/加字段/改交互/加状态），右侧说明必须在同一次交付里同步更新；交付时还要给出**概括性的「需求说明更新摘要」**（按菜单分组、每条一句话 + 单列原型改动 + 提醒留空待填项）

## 人工修改回传流程（方案 A，务必照做）

**背景**：用户在浏览器里改说明 → 改动落在浏览器缓存 → 磁盘上的 index.html 没变 → Agent 看不到。这是浏览器沙箱的硬边界（`file://` 页面对磁盘只有读权限，**无法自动写回**）。所以回传只能靠"导出"。

**触发**：用户说"我在页面上改好了 / 导出文件在 xxx / 帮我把浏览器里改的合并一下"，或直接给了一个 `*-原型-YYYYMMDD-HHMMSS.html` 路径。

**步骤**

1. 确认两个路径：**来源**＝用户导出的 html；**目标**＝原型原文件 `<原型目录>/<系统>/index.html`
2. 先干跑看一眼：
   ```
   node "<skill>/scripts/merge-spec.js" <导出文件> <目标index.html> --dry-run
   ```
3. 干跑无异常 → 去掉 `--dry-run` 执行。脚本会自动备份、替说明区、换 key、打报告
4. 把报告的「改动摘要」复述给用户（新增几个章节、几处人工定稿标记）
5. 告诉用户目标文件的绝对路径，请他刷新页面查看

**遇到 `[中止]` 怎么办**，按报告里的原因处理：
- **缺失菜单 / 功能点**：用户是拿旧版改的。先告诉用户缺了什么，请他打开最新版重新再改一次导出；用户明确说"就是要这样"才加 `--force`
- **目标文件在导出之后被改过**（报告列出会被冲掉的 Agent 改写内容）：先把列出的内容告诉用户，请他打开最新版 index.html，把浏览器里的改动重做一遍再导出；用户明确说这些 Agent 改写可以丢掉，才加 `--force`
- **导出文件里有脚本或不认识的事件属性**：这一项 `--force` 也不放行。告诉用户导出文件被改过或来源不明，请他从原型页面重新导出

**结算后必做**：后续迭代时，带 `data-user-edited` 标记的内容 = **用户的定稿**，不许覆盖。要改就停下来问。

## 对话修改需求说明流程（场景 C）

> 用户不打开浏览器，直接跟你说「帮我改下需求说明里的 xxx」。**默认只改右侧 `#specBody`，左侧原型一字不动。**

### 步骤（顺序不能反）

1. **冲突预检（必做，别省）**
   问一句：「你最近在浏览器里改过说明吗？改过的话先点『导出 HTML』把文件给我，我这次改完会换缓存 key，没导出的改动会丢。」
   - 用户给了导出文件 → **先跑场景 B 合并**，再做本次修改
   - 用户说没改过 / 直接改 → 继续
2. **定位**：`node "<skill>/scripts/edit-spec.js" <index.html> --list`
   输出菜单 → 功能点 → 子项 → 表格列权限（🔒/✏），照着它找到要改的 `<div class="sub-v">` 或 `<td>`
3. **一致性判定**：用下表判断这次改动会不会让说明与原型对不上，命中 ✅ 先问用户
4. **备份基线 + 换 key**：`node "<skill>/scripts/edit-spec.js" <index.html> --bump-key`。**必须在改内容之前跑**：它保存的是改动前的文件，`--verify` 拿它当比对基线
5. **改内容**：只改 `#specBody` 内的内容；改动的 `[data-edit]` 单元格顺手打 `data-agent-edited="1"`
6. **校验**：`node "<skill>/scripts/edit-spec.js" <index.html> --verify`，退出码非 0 时按输出逐项处理
7. **交付**：给出 index.html 的绝对路径，按下方「交付时告诉用户」说明

### 一致性判定表（哪些改动必须与原型同步）

| 改动类型 | 例子 | 要动原型吗 |
|---|---|---|
| 纯文案润色 / 补充说明 | 交互描述改写、业务规则再补一条、备注填写 | ❌ 直接改 |
| 补用户侧业务口径 | 权限表填角色、数据权限口径、状态流转、指标公式（这些本来就是留空给用户填的） | ❌ 直接改 |
| 改「交互」形态 | 弹窗 ↔ 独立页面、按钮挪位置、入口变了 | ✅ **先问** |
| 增 / 删 / 改功能点 | 加一个「批量导入」功能点、删掉某个功能点 | ✅ **先问** |
| 改锁定列（🔒）内容 | 字段名、列表元素名、字段类型、功能点名称 | ✅ **先问** |
| 字段 / 列表列增删 | 字段表里加一行「客户等级」 | ✅ **先问** |
| 状态、筛选、排序变化 | 新增「已流失」状态、加「按意向等级筛选」、改默认排序 | ✅ **先问**（原型要有对应入口） |

**命中 ✅ 时停下来问**，给两个选项：
1. **只改说明**，并在该处标注「原型待补充」（说明先记着，原型后补）
2. **说明 + 原型一起改**（按 `add-menu-checklist.md` 的 A/B 节同步改左侧）

禁止擅自改原型，也禁止把说明改成原型上没有的样子却不提醒。

### 脚本

```
node "<skill>/scripts/edit-spec.js" <index.html> --list        # 定位：列出说明区结构与列权限
node "<skill>/scripts/edit-spec.js" <index.html> --bump-key    # 备份改动前的文件 + 换 PROTO_KEY（改之前跑）
node "<skill>/scripts/edit-spec.js" <index.html> --verify      # 校验：与最近一次 --bump-key 的备份比对
node "<skill>/scripts/edit-spec.js" <index.html> --check       # 自检：生成或迭代原型后检查结构
node "<skill>/scripts/edit-spec.js" <index.html> --norm        # CRLF→LF（多行替换匹配失败时先跑它，会先备份）
```

`--verify` 比对最近一次 `--bump-key` 留下的备份（合并留下的备份不参与）：原型模板/脚本有改动会报 ❌，🔒 锁定单元格内容变了会报 ⚠️ 并列出差异，人工定稿标记变少会报警。**退出码非 0 = 有需要人工确认的项。**

脚本用正则读取说明区，手工改说明时保持模板里的写法：`<div class="sub"><div class="sub-k">…</div><div class="sub-v" …>…</div></div>` 之间不加换行，`menu-pane` 的属性顺序保持 `class`、`data-menu`、`data-label`，`fn item` 卡片保持 `class`、`data-k` 在前。

### 交付时告诉用户

- 改了哪几处（菜单 / 功能点 / 子项）
- 是否动过原型（默认没动；若命中 ✅ 且用户选了同步改，说清原型改了什么）
- **刷新页面才看得到**，且如果在浏览器里还有没导出的改动，这次换 key 后会失效

## 导出需求说明 Markdown（场景 D）

> 用户要拿走说明文本去发人 / 贴文档。**只生成副本，原型文件与说明内容一律不动。**

**步骤**

1. **冲突预检（必做）**：先问「你最近在浏览器里改过说明吗？」
   - 改过 → 让他先「导出 HTML」，走场景 B 合并回原文件，**再**生成 md。否则 md 里会缺他改的内容（脚本读的是磁盘文件，读不到浏览器缓存）
   - 没改过 → 直接生成
2. **生成**（Agent 执行，用户不需要任何操作）：
   ```
   node "<skill>/scripts/edit-spec.js" <index.html> --to-md
   ```
   输出 `<模块名>-需求说明-<时间戳>.md` 到原型同目录，结构：`# 菜单名 → ## 章节 → ### 编号 功能点 → 子项（表格 / 分条规则）`；留空项写「（待补充）」
3. **交付**：给出 md 文件的绝对路径，并说明「这是快照副本，改它不会影响原型；要同步回原型得把改的内容发给我」

**注意**：**不要**为了这个需求去页面上加「导出 Markdown」按钮，规范里明确不许加。

## 关键技术机制（写错了功能会坏）

| 机制 | 要点 |
|---|---|
| Vue 挂载 | 左侧模板放 `<script type="text/x-template" id="protoTpl">`，Vue 用 `template:` 挂载，挂载前用 `HUI_COMPONENTS` 注册模板封装好的组件。否则导出重开时指令全丢、交互失效 |
| 界面样式 | 加载 `@heroui/styles@3.2.6/dist/heroui.min.css` 和 `@tailwindcss/browser@4.1.13`；左侧控件用模板封装的 `<hui-select>`、`<hui-checkbox>`、`<hui-radio-group>`、`<hui-tabs>`、`<hui-modal>`、`<hui-drawer>`、`<hui-menu>`、`<hui-search>`，其余用 HeroUI 类名（`button`、`card`、`chip`、`table-root`、`avatar`、`pagination`）。HeroUI 读状态属性不读原生状态（复选框 `data-selected`、页签 `data-selected`、下拉框 `data-open` / `data-empty`），弹窗、抽屉的 `data-placement` 要写在 container 和 dialog 上，详见规范第六章 |
| 图标 | lucide 1.60.0 内联 SVG：左侧 `<lc-icon name="...">`（路径在 `ICONS`），静态 DOM 直接写 `<svg class="lucide">`；禁止 emoji 图标 |
| 编号气泡类名 | `num-badge` / `num-badge-in`，不能叫 `badge`（HeroUI 同名组件类会改掉样式） |
| 导出给 AI | 工具条按钮打开静态弹窗 `#aiPromptModal`（在 `#specBody` 之外），`aiPrompt()` 从说明区 DOM 生成提示词，空项写「未提供，需确认」；复制、下载 `.md`；只出不进，不改说明、不换 key |
| 右侧说明 | 必须是 `#app` **之外**的静态 DOM，Vue 不托管。否则 Vue 重新渲染会冲掉用户编辑的内容 |
| 菜单切换 | Vue `switchMenu(m)` 同步左侧菜单/内容区 + 调 `window.showMenuPane(m)` 切右侧 pane；当前菜单记在 `<body data-active-menu>` |
| 编号联动 | 编号单位 = **功能点**（不是交互步骤）；同一功能点的多个入口挂同一编号。**点左侧气泡 → 右侧平滑滚动定位到该功能点卡片**（`scrollIntoView smooth center`）；点右侧卡片只走卡片自己的 `onclick="flashAllNoScroll(k)"`，不滚动，**不要再加 document 级的 `.item` 点击监听**（会对同一次点击再执行一次带滚动的 `flashAll`）。`flashAll()` 用 `offsetParent` 过滤，只点亮当前可见 pane 内元素；各菜单独立从 ① 编号 |
| 工具条 | 吸附右侧说明区**底部**（`sticky bottom-0`），放在 `</aside>` 前、`#specBody` **之后**——放进 specBody 会被 localStorage 存进去导致重复渲染 |
| 说明显隐开关 | 左侧包一层 `<div id="protoWrap" class="relative shrink-0">`，里面放 `#app` 和 `<button id="specToggle">`。宽度用 CSS 控制（`#protoWrap{width:62%}` / `body[data-spec="hidden"] #protoWrap{width:100%}`），**不要写死在 `#app` 的 class 上**。开关必须在 `#protoWrap` 内、`#app` 外（放进 app 会被 Vue 覆盖）。状态存 `<body data-spec>` + `PROTO_KEY+':hidden'`；`flashAll` 开头检测到隐藏态要自动展开 |
| 列级锁定 | 锁定单元格写 `<td class="lock">`（不加 `data-edit`，编辑态不变黄）；可编辑写 `<td data-edit>`；表格禁止增删行 → 不加 `data-editable-table`。**表单类字段表列权限分两种**：新增类=仅备注可改；编辑类=必填/校验规则/默认值/备注四列可改 |
| 持久化 | 一个 `PROTO_KEY` 存 `#specBody.innerHTML`（含所有 pane）；导出 HTML 时换新 key，保证链式迭代可继续编辑；**结构变更时必须手动换 key** |
| 导出基线 | 导出 HTML 时在 `#specBody` 上写 `data-base-key`＝用户打开的原型文件的 `PROTO_KEY`（从导出文件再导出时保留原值）。合并时与目标文件当前的 `PROTO_KEY` 比对，不一致说明目标在导出之后被改过；合并写入时去掉这个属性 |
| 人工定稿标记 | `onEdit` 里对被编辑的 `[data-edit]` 打 `data-user-edited="1"`；`addSection` 新建的章节整块打标。标记随 innerHTML 导出，是 Agent 识别"用户改过"的唯一依据 |
| Agent 改写标记 | 场景 C 里 Agent 改过的单元格打 `data-agent-edited="1"`（用户级标记是 `data-user-edited`）。两个标记共存时以用户为准；合并时用它找出会被冲掉的 Agent 改写 |
| 场景 C 校验 | `--verify` 比对 protoTpl + 脚本 hash（**已排除 PROTO_KEY**，否则必报假差异）+ 🔒 锁定单元格文本集合 + 人工标记数 |
